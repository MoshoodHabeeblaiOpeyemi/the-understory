You type `readunderstory.ink` into your browser. You hit enter. Half a second later, a page appears. Somewhere in that half-second, your browser sent a small text message to a server, and the server sent one back. Those messages have a name. They have a structure. And once you learn to read them, you'll never look at the web the same way again.

That message format is called **HTTP**. It's the language of the web. And today, we're going to learn to speak it — and read it — properly.

## Not a program — a language

First, the most important thing to clear up: **HTTP is not software.** It's not something you install. It's a **protocol** — a set of rules for how two computers should talk.

**HTTP** stands for **HyperText Transfer Protocol**. Every word matters:

- **HyperText** — text that links to other text. The "hyper" refers to the links that let you jump from one document to another. That was the original revolutionary idea of the web.
- **Transfer** — it moves things from one place to another.
- **Protocol** — an agreed-upon set of rules. Like diplomatic protocol at a state dinner. Everyone knows how to behave.

**Analogy:** HTTP is like a formal letter-writing convention. If we both agree to write letters with a date at the top, a recipient below that, a greeting, a body, and a signature — we can communicate even if we've never met. HTTP is that convention, but for computers, and about a thousand times faster.

## HTTP is text (mostly)

Here's the beautiful truth: **HTTP messages are readable text.** You can literally watch them being exchanged. You can write one by hand. You can read one in your browser's DevTools.

Before HTTPS became standard, you could open a network tool and see every word being said. Now with HTTPS, everything's encrypted — but conceptually, the messages are still simple text underneath.

**Analogy:** Think of HTTP as writing letters in plain English. Anyone who intercepts the letter can read it. **HTTPS** is writing the same letters in a secret code that only you and the recipient can unlock. The *format* of the letter is still the same — the *contents* are scrambled.

We'll get to HTTPS properly in a bit. First, let's learn the language itself.

## The anatomy of a request

Every HTTP **request** — what the client sends — has three parts:

```
1. A request line
2. Headers
3. (Sometimes) a body
```

Let's look at what a real one looks like.

```http
GET /about HTTP/1.1
Host: readunderstory.ink
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7)
Accept: text/html
Accept-Language: en-US,en;q=0.9
Connection: keep-alive
```

That's it. That's a complete HTTP request. Four headers, one request line, no body. Small enough to fit on a napkin. And this is what your browser is sending to websites millions of times per day.

Let's break it down.

### The request line

```
GET /about HTTP/1.1
```

Three pieces, in order:

- **`GET`** — the **method**. It says what kind of action you want to perform. "Get this thing for me." We'll do a full day on methods tomorrow.
- **`/about`** — the **path**. It says which resource you want. Everything on a server has a name, and this is the name you're asking for.
- **`HTTP/1.1`** — the **protocol version**. Says which version of the HTTP rules you're speaking. (We're now on HTTP/2 and HTTP/3 in modern browsers — but HTTP/1.1 is still the clearest to read and learn from.)

### The headers

```
Host: readunderstory.ink
User-Agent: Mozilla/5.0...
Accept: text/html
Accept-Language: en-US,en;q=0.9
Connection: keep-alive
```

**Headers** are little `key: value` pairs that give extra context about the request.

- **`Host`** — which website you're asking about. Yes, this seems obvious, but one server can host many websites. This tells it which one you want.
- **`User-Agent`** — what client is making the request. "Hi, I'm Chrome on a Mac." Servers use this to serve different content to different browsers or devices.
- **`Accept`** — what format the client can handle. "I can take HTML." This is the client being polite about its preferences.
- **`Accept-Language`** — what language the client prefers. "I speak English, but French would be OK too." This is how websites know to show you English.
- **`Connection`** — should the connection stay open after this request? `keep-alive` means "yes, I'll probably make more requests, don't hang up."

**Analogy:** If the request line is the question ("Can I see the About page?"), headers are the context around it: who's asking, what language they speak, what format they want the answer in, and whether they're planning to ask more questions.

### The body (optional)

Most `GET` requests don't have a body. But when a client is *sending* data — like a login form, a post submission, a file upload — the body carries that data.

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 47

{"username": "ada", "password": "secret123"}
```

See the JSON at the bottom? That's the body. It's the payload — the actual thing being sent.

The headers are still the context, but now they include `Content-Type` and `Content-Length`, telling the server what kind of data is coming and how big it is.

## The anatomy of a response

Now the server replies. Every HTTP **response** also has three parts:

```
1. A status line
2. Headers
3. (Usually) a body
```

Here's what a response looks like:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1284
Cache-Control: max-age=3600
Set-Cookie: session=abc123; Path=/; HttpOnly

<!DOCTYPE html>
<html>
  <head><title>About</title></head>
  ...
</html>
```

### The status line

```
HTTP/1.1 200 OK
```

Three pieces:

- **`HTTP/1.1`** — protocol version.
- **`200`** — the **status code**. Three digits. Tells you how the request went. We'll do a full day on these soon.
- **`OK`** — the **reason phrase**. Human-readable label for the code. Purely descriptive — programs care about the number, not the words.

### The headers (again)

```
Content-Type: text/html; charset=utf-8
Content-Length: 1284
Cache-Control: max-age=3600
Set-Cookie: session=abc123; Path=/; HttpOnly
```

Server headers do the same job client headers do — provide context. Some important ones:

- **`Content-Type`** — what kind of content is in the body. "This is HTML." Or "This is JSON." Or "This is a JPEG."
- **`Content-Length`** — how big the body is, in bytes.
- **`Cache-Control`** — how long the client should cache this. "You can keep this for an hour before asking again."
- **`Set-Cookie`** — tells the client to store a cookie. We'll do a day on this too.

### The body

The body is the actual content — the HTML of the page, the JSON of an API response, the bytes of an image.

For the About page we requested, the body is the HTML that renders the page. Simple.

## The devil in the details: character encoding and mojibake

Let's pause here, because this is where a lot of real-world bugs live — and where a word you asked about finally makes sense.

Look at this header again:

```
Content-Type: text/html; charset=utf-8
```

That `charset=utf-8` is doing more than it looks like. It's telling the client **which character encoding to use to read the bytes of the body.**

A **character encoding** is a system for mapping numbers to characters. Computers only understand bytes — numbers from 0 to 255. To store text, you need a convention: "this number means this letter."

- **ASCII** — the oldest. Only 128 characters. English letters, digits, punctuation. Cannot represent `é`, `ñ`, `ọ`, Chinese, Arabic, emoji, or anything non-English. This is why the early internet was English-centric.
- **Latin-1 (ISO-8859-1)** — extended ASCII to 256 characters. Added Western European accented letters. Still can't handle most languages.
- **UTF-8** — the modern standard. Can represent **every character in every human language**, plus emoji. It's a variable-length encoding: common English letters take 1 byte, others take 2–4. This is what the web uses now, almost universally.

**Here's where it goes wrong:** if the server says "this content is UTF-8" but the client reads it as Latin-1 (or vice versa), the bytes get misinterpreted and you get garbage on screen.

That garbage has a name. That name is **mojibake**.

You've seen it. Maybe you've seen it without knowing what it's called:

The word comes from Japanese: **文字化け** — *moji* (character) + *bake* (transform, change). Literally "character transformation." Japanese developers named the phenomenon in the 1980s when it plagued their systems, and the word stuck in English because there was no better one.

**Analogy:** Imagine you hand someone a letter written in Russian Cyrillic, and they try to read it using the English alphabet's rules. Every letter becomes nonsense. They're reading real symbols — they're just using the wrong key. Mojibake is exactly that, but for bytes.

**Why you should care:** if you ever build an API, serve a file, or render user-submitted text, and you forget to declare (or correctly handle) encoding — you'll see mojibake. And so will your users. The fix is almost always: **declare `charset=utf-8` in your `Content-Type` header, and make sure your text actually *is* UTF-8.**

That's why the header matters. It's a tiny string that decides whether a page reads beautifully or looks like a broken password.


## HTTP is stateless — and that's a bigger deal than it sounds

One concept before we get to HTTPS. It's short but essential.

**HTTP is stateless.** Every request is independent. The server doesn't remember your last request. It doesn't remember your name. It doesn't remember you logged in two seconds ago.

**Analogy:** Imagine going to a market where the trader has amnesia. Every time you walk up to her stall, she has no idea who you are or what you bought five minutes ago. You'd have to reintroduce yourself and re-explain your situation every single time.

That's HTTP. Every request is a stranger. Every response is a fresh start.

So how do websites know you're logged in? How does Twitter remember your feed? How does Gmail know your emails are yours?

The answer is a mechanism called **cookies** — a way of storing a small piece of data on the client, which it sends back with every request, so the server can recognise you. Cookies are how stateless HTTP pretends to have a memory.

We'll do a full day on cookies and sessions soon. For now, just sit with this: **HTTP remembers nothing. Everything that feels like memory is a clever trick built on top.**

## HTTPS — the same language, but encrypted

Now we get to HTTPS. And the good news is: **HTTPS is just HTTP with encryption**.

That's genuinely it. Same request format. Same headers. Same status codes. Same body structure. Same everything. The only difference is that the whole conversation is wrapped in a cryptographic layer that makes it unreadable to anyone listening in the middle.

**HTTP** = plain text. Anyone can read it.
**HTTPS** = encrypted. Only the client and server can read it.

The "S" stands for **Secure**. And that secure layer is called **TLS** — **Transport Layer Security**.

### A brief note on SSL vs TLS

You'll hear "SSL" everywhere. It's technically wrong. Here's the story:

- **SSL** (Secure Sockets Layer) was the original encryption protocol, invented by Netscape in the mid-1990s.
- SSL 1.0 was never released. SSL 2.0 came out in 1995. SSL 3.0 in 1996.
- SSL 3.0 had serious flaws. So in 1999, a new protocol was created called **TLS 1.0** — basically SSL 3.0 with the vulnerabilities fixed.
- TLS 1.1, 1.2, and 1.3 followed. We're on TLS 1.3 now.
- But the world got used to saying "SSL." So even though the actual protocol is TLS, everyone — including most developers — still says "SSL."

**Rule of thumb:** say TLS when you want to sound precise. Say SSL when you want to sound normal. Either way, you're referring to the same layer.


### How the padlock works

When you see the padlock in your browser's address bar, here's what's actually happening under the hood — in three steps:

1. **The handshake.** When your browser connects to an HTTPS server, they do a cryptographic dance called a **TLS handshake**. Your browser says "hello." The server sends back its **certificate** — a digital document that proves its identity. The browser checks the certificate against a list of trusted authorities. If it checks out, they agree on an encryption key.
2. **The tunnel.** Once the handshake is done, both sides share a secret key. Everything from here on out — every request, every response — is encrypted with that key before it goes over the wire.
3. **The verification.** If the certificate doesn't check out, or if it's expired, or if it belongs to a different domain, your browser shows a big scary warning. That's the padlock breaking.

**Analogy:** Imagine you're sending a letter to a bank. You want to be *sure* the letter reaches the real bank and not a criminal impersonating one. HTTPS is a system where the bank publishes a public stamp that only the real bank can make, and your browser checks that stamp before trusting anything.

### What HTTPS actually protects against

Three main things:

- **Eavesdropping** — someone on the same WiFi can't read your messages. In an open café WiFi, without HTTPS, anyone nearby could read your passwords. With HTTPS, they just see garbled bytes.
- **Tampering** — a middle-man can't modify your data in transit. Your bank statement can't secretly be changed to say you have ₦50 instead of ₦50,000.
- **Impersonation** — a fake server can't pretend to be your bank. The certificate proves identity.

This is why browsers now actively shame HTTP sites. Chrome and Firefox flag plain HTTP as "Not Secure" in the address bar. It's not a suggestion anymore — HTTPS is the default.

### A bit of history

The story of how HTTPS went from rare to universal is worth knowing — because it shows how the web evolves.

**1994** — Netscape invents SSL for its browser. HTTPS is born, but only used for login forms and payment pages. Everything else is plain HTTP.

**2000s** — HTTPS is still a niche tool. Only banks and e-commerce sites use it. Regular websites are still HTTP. Passwords get sniffed on public WiFi. It's the wild west.

**2010** — Google starts using HTTPS as a **ranking signal**. Sites with HTTPS rank slightly higher in search. This nudges companies to adopt it.

**2014** — **Heartbleed** — a catastrophic bug in the OpenSSL library — exposes how fragile the trust model is. Also in 2014, Google proposes "HTTPS everywhere" and starts making HTTPS a requirement for many features.

**2015–2018** — The Let's Encrypt project launches, offering **free HTTPS certificates**. Before this, a certificate cost $50–$100 and required paperwork. Now anyone can get one in seconds. The barrier to HTTPS collapses.

**2018–now** — Browsers mark all HTTP pages as "Not Secure." HTTPS becomes the default. Over 95% of web traffic is now encrypted. The web is basically HTTPS-only.

**The takeaway:** the web isn't static. Things that seem permanent — like "most sites are HTTP" — can shift in under a decade. Technologies you learn today may be industry standard tomorrow.

## What you'd say in the room

If an interviewer asks *"What's the difference between HTTP and HTTPS?"* — here's the answer:

> "HTTPS is HTTP wrapped in TLS encryption. The HTTP request-response format is identical — same methods, headers, status codes, body. The difference is that with HTTPS, the entire conversation is encrypted. When a client first connects to an HTTPS server, they do a TLS handshake where the server proves its identity with a certificate, and both sides agree on an encryption key. Everything after that is encrypted. HTTPS protects against eavesdropping, tampering, and impersonation. Modern browsers flag HTTP sites as 'Not Secure,' and today over 95% of web traffic is HTTPS."

That's a whole answer. Learn it.
